# Retro Set: guide for AI assistants and developers

This is the main guide for anyone, person or AI, who changes this project. Claude Code reads it through `CLAUDE.md`; other AI coding tools (OpenAI Codex, Cursor, GitHub Copilot and others) read `AGENTS.md` directly. A chat AI that can't open the repository can be given `CONTEXT.md` instead: this guide, the other notes, a map of the code and the full source in one file (`CONTEXT-SHORT.md` is the same without the source).

## Start here

**What it is.** Retro Set is a 3D pixel-art chess game, a sister to the owner's pool game Retro Rack (https://github.com/flopp-r/retro-rack, live at https://flopp-r.github.io/retro-rack/). Like Retro Rack it is one self-contained web page, hosted on GitHub Pages from this repository, and installable as an app. Live: https://flopp-r.github.io/retro-set/

**Where it's up to.** The owner chose 3D pixel art, classic piece shapes, the full rules without clocks, and all three ways of playing, built in stages (`HANDOVER.md`, section 4). Stage 1: two players on one device, with the full rules, take back, resigning, agreed draws, and Resume after a reload. Stage 2: ten computer opponents from 100 to 1500 (Torben to Ted), their strength measured against Stockfish and each other. Stage 3: online play, as close to Retro Rack's as possible, through a relay of its own (`relay/`, deployed as the Cloudflare Worker `retro-set-relay`, its address in `config.js`). All of it is live, and the owner has confirmed it works (10 November 2026). A second round was then agreed, in four parts, each its own pull request (`HANDOVER.md`, section 4, "The second round"): the pieces redesigned with seven piece sets and separate finishes (live, see Piece sets and finishes), then tabbed menus and settings (live, see Settings and the menu's tabs), then the cosmetics: a locker and a shop with five rarities, cases and keys (live, see Cosmetics), then trading between players (built, waiting to be merged, see Trading), then a story mode against the bots. Ask the owner the questions each part needs before building it, and agree any other change first: the open decisions and the ideas are in `HANDOVER.md` (sections 4 and 7).

**Read in this order**
1. This file: how it works, the rules, and how to test and ship a change.
2. `HANDOVER.md`: why things are the way they are, reference numbers, the decisions still to make, and a dated list of every change shipped.
3. `README.md`: how the owner set it up, and what players see.
4. The code: `src/core.js` (the chess rules and the computer player's engine), `src/bots.js` (the computer opponents), `src/looks.js` (the cosmetics' rules), `src/sets.js` (the piece sets and finishes), `src/game.js` (everything in the browser, online play included), then `relay/src/index.js` (the relay). The JavaScript files are split into sections marked `// ------ name`; the map in `CONTEXT.md` lists them with line numbers.

**Rules that must never be broken**
1. **`index.html` is built output.** Edit `src/`, then run `node tools/build.js`, and commit both.
2. **A clean console:** no errors, warnings or deprecated APIs.
3. **`main` is live.** Pushing to `main` deploys the site. Work on a branch and test first.
4. **`src/core.js`, `src/bots.js` and `src/looks.js` have no DOM.** The rules, the engine, the bots and the cosmetics' rules must also run in Node, for the tests and tools.
5. **A bot's rating is measured, never guessed.** Changing the engine (evaluation, search) or a bot's settings changes its strength: re-run `node tools/sim-bots.js tune`, put the new values into `src/bots.js`, then `check`, and record the results in `HANDOVER.md` (section 5).
6. **The repository is public.** Never commit personal details, passwords, tokens or keys.
7. **Online play needs both players on the same version,** and both browsers must agree on every position. Ask the owner before changing online messages or behaviour, keep old fields working where possible, and test with the local relay (see Commands) before merging.

## Project conventions

- Explain changes in plain language, say what will change on screen, and keep jargon out of summaries.
- UK English and metric units everywhere: in the UI, comments and messages.
- Ask before large redesigns, as well as before anything that changes online play (rule 7 above).
- Every menu screen must fit a phone held sideways (762×341) without scrolling. A long list may scroll inside its panel; the screen itself still fits.
- Code style: match the file you're in. Compact, mostly one statement per idea, comments only where the reason isn't obvious. No build step beyond `tools/build.js`, and no frameworks or npm packages in the game.
- A piece set must stay readable: every kind a different shape from the rest, not the same shape at another size, and the pawn and the bishop most of all (the `sets` browser test measures it).
- Browser storage keys start with `retroSet.` (Retro Rack's start with `retroRack.`, so the two games never read each other's saves on the same site): `retroSet.settings`, `retroSet.game`, `retroSet.menu`, `retroSet.name` (the online name), `retroSet.rejoin`, `retroSet.rotateHint` (the sideways hint dismissed), `retroSet.locker` (the cosmetics), and `retroSet.dev` and `retroSet.lockerDev` (dev mode and its test locker) so far; sessionStorage, per tab, `rs.cid` and `rs.live` (see Online play). Wrap every access in try/catch: storage can be missing or blocked.

## Commands

No installs are needed for the game itself, only Node.

- `node tools/build.js`: rebuild `index.html` after any change in `src/`. It also remakes `CONTEXT.md` and `CONTEXT-SHORT.md`, so run it after changing the notes too.
- `node tests/core.test.js`, `node tests/bots.test.js` and `node tests/looks.test.js` (`npm test` runs all three): the rules, the engine and the cosmetics tests. They must pass before pushing.
- `node tools/sim-shop.js [players] [wins a day]`: how many days pretend players take to fill the locker (400 players and 3.5 wins a day by default). Run it after changing a price, the odds or what a game pays, and record the result in `HANDOVER.md` (section 5).
- `node tools/sim-bots.js match <a> <b> [games]`: play two players against each other and print the score and the rating gap (a bot such as `ted`, a bot with another knob or depth such as `ted@0.05/4`, or Stockfish at a strength such as `sf1500`). `tune [games]` finds every bot's knob (about 1½ hours on 4 cores); `check [games]` measures them all. The first run installs Stockfish (npm) into a temporary folder.
- `node tests/browser/run-all.js [words]`: run the browser tests (all of them, or only files whose names contain the words). See Testing.
- `node tools/make-icons.js`: redraw the app icons (pixel art, no installs). The build inlines `icons/favicon-32.png`.
- To look at the game: open `index.html` in a browser. The installable-app parts need the page served over http, since service workers don't run from `file://`; the `app` browser test does that.
- Relay, locally: `cd relay && npm install && npx wrangler dev --port 8797`. Then open `index.html?relay=ws://127.0.0.1:8797` in two separate browser windows to play yourself online.

## Architecture

### Core (`src/core.js`)
- One object, `CORE`, made inside a function so nothing leaks into the page; at the bottom, `module.exports = CORE` when running in Node. The build puts it first in the page, so `game.js` uses it as `C`.
- **Squares** are numbered 0 to 63: a1 = 0, b1 = 1 … h8 = 63 (rank × 8 + file); `sq('e4')` and `sqName(28)` convert. **Pieces** are letters, `PNBRQK` White and `pnbrqk` Black (`colour()`, `kind()`).
- **A position** is `{ b, turn, castle, ep, half, full }`: `b` is 64 strings (a piece letter, or `''` for an empty square), then who moves (`'w'`/`'b'`), the castling rights (`'KQkq'` or part of it), the en passant square (or -1), the halfmove clock (moves since a capture or a pawn move) and the move number. `parseFen()` and `toFen()` read and write FEN (Forsyth–Edwards Notation); `START` is the starting position.
- **Moves:** `legalMoves(pos)` gives every legal move as `{ from, to, p, cap, promo, ep, dbl, castle }` (the piece, the piece taken, what a pawn becomes, an en passant capture, a pawn's two-square advance, `'K'` or `'Q'` for castling). `pseudoMoves()` makes them, and a move is legal if the mover's king isn't attacked afterwards (`attacked()`, `inCheck()`). `makeMove()` returns the next position; castling rights go when the king or a rook moves or a rook is taken on its home square (`LOSE`). `perft(pos, n)` counts the positions n moves on, the standard check on move generation.
- **Games** never change: `newGame(fen)`, `play(game, { from, to, promo })` (null if the move isn't legal), `playUci(game, 'e2e4')`, `undo(game)` and `finish(game, score, why)` (resigning, an agreed draw) each return a new game `{ start, pos, list, keys, result }`. `list` holds each move with its notation (`san()`: Nf3, exd5, O-O, e8=Q+, Qh4#) and the position after it; `keys` the repetition key of each position (`repKey()`: the pieces, the side to move, castling, and an en passant square only when the capture can really be played).
- **The end** (`judge()`, after every move): checkmate, stalemate, a third repetition, fifty moves each with no capture or pawn move, and too few pieces to mate (`deadPosition()`: kings alone, one bishop or knight, or only bishops all on one colour of square). The repetition and fifty-move draws happen at once, as on most online sites, rather than being claimed. `result` is `{ score: '1-0' | '0-1' | '1/2-1/2', why }`, `why` one of `checkmate`, `stalemate`, `repetition`, `fifty`, `material`, `resigned`, `agreed`.
- **The computer player** (the computer player section): `evaluate(pos)` scores a position for the side to move in centipawns (100 = a pawn): material (`VALUE`) and where the pieces stand (`PST`, the "simplified evaluation function" tables; the king's table moves from sheltering to coming out as pieces come off), passed pawns (more the further on), doubled and isolated pawns, rooks on open files, the bishop pair, and the king's pawn shelter while there's a middlegame. `negamax()` searches a set number of moves ahead with alpha-beta pruning, captures first (`order()`), one move further when in check; `quiesce()` then follows captures until the position is quiet. `think(game, cfg, rnd)` chooses a move: it scores every legal move by searching the reply and adds the bot's style bonuses. Then, with chance `cfg.blunder`, it blunders: of the moves scoring at least `BLUNDER` (200 centipawns: a piece, two pawns, or walking into a mate, or missing one) below the best, it picks the one that looks best at a glance (the position straight after the move, not the reply: grabbing a pawn the queen can't hold, say); if no move is that bad, it plays as usual. Otherwise it picks with a softmax over the scores at temperature `cfg.temp`: the higher, the likelier a middling move. Looking one move ahead (`depth` 1) with captures followed through, it sees a piece left to be taken but not a fork, a pin or any other threat (the low bots' blind spot); it also checks for a mate in one and a stalemate. Without following captures (`qs` false) it grabs defended pieces and loses them: measured, that is weaker than the 100 bot even at its best, so every bot follows captures through. A move repeating the position a third time scores 0. In the first 8 moves the temperature is at least 30, so games don't all open the same way. Moves scoring far below the best so far are only searched far enough to show it (the `floor`).
- Two habits carried over from Retro Rack: no `Math.random` in `core.js` (choices take a seeded generator, `rng(seed)`, so a test or a measurement repeats exactly), and the computer player as a generator (`think` is a `function*`, yielding after each move it scores, so the page spreads the thinking over frames; `runThink()` runs it to the end at once, for the tests and tools).

### The bots (`src/bots.js`, `tools/sim-bots.js`)
- `LIST` holds the ten bots, weakest first: Torben 100, Alfie 250, Ollie 400, Dom 550, Joseph 700, Barney 850, Magnus 1000, Jake 1150, Daws 1300 and Ted 1500 (names chosen by the owner). Each has `id`, `name`, `rating` (the target it was tuned to), `look` (the portrait), `blurb` (the line on the picker) and `cfg`: `depth`, `qs` (follow captures through: every bot does) and `blunder` (the chance each move of a real blunder, 30% for Torben falling to 3% for Ted) chosen by hand; `k` (the strength knob) found by `tools/sim-bots.js`; and `style` bonuses for the moves the bot likes (`capture`, `check`, `pawn`, `castle`, `queen`, centipawns). `knob(k)` turns k into `temp` (0 is the engine's best at that depth; from 1.4 it's close to random); `settings(bot)` gives `think()` its full settings. `RENAMED` maps the bots from before the renaming (Pip, Mabel, Dev, Priya, Gus, Ruth, Tariq, Nell) to the nearest new one, so `byId()` still finds a saved game's or menu choice's bot.
- **How the ratings are anchored:** Ted (1500) is tuned to score 50% against Stockfish at `UCI_Elo` 1500, and Daws (1300) to score 47% against Stockfish at 1320 (its lowest setting, so 20 points above him). Each bot below is tuned to score 30% against the one above it, which is what a 150-point gap means (`CHAIN`, made from the list). Stockfish's strength setting is calibrated by its makers against engine rating lists (CCRL), not against people, and the gaps are measured between bots, so the ratings are as accurate as that anchor and the number of games (`HANDOVER.md`, section 5, has the measured figures with their margins). They are not chess.com ratings: chess.com's, lichess's and FIDE's scales differ, by hundreds of points at the low end.
- **`tools/sim-bots.js`** plays games in worker threads (one a core): bots run `runThink()`, Stockfish (stockfish.js 19, the full single-threaded engine, as a child process speaking UCI) gets 60 ms a move, which is plenty at its weakest settings since they choose after a very shallow search. A game still going after 240 half-moves is decided on material (a side three pawns ahead wins, else a draw); one a clear rook-and-minor ahead for 6 half-moves after move 15 is stopped as won. `tune` starts from each bot's current knob, steps by 0.03 until its target lies between two tries, then closes in by straight-line steps in rating points; `check` replays each bot against its reference and prints its rating, built on the reference's measured rating, with the margins added up. Both can start part-way down the chain (`tune 80 jake`, `check 240 daws`).

### Browser (`src/game.js`)
- **Rendering** (the renderer + post section, the same as Retro Rack's): the scene is drawn at low resolution into a render target; a post-processing shader then adds outlines where the depth jumps, a vignette and, below full colour, Bayer dithering and colour quantisation; the canvas is scaled up with hard pixel edges. Lights use three.js physical units; colour management is off, so colours appear exactly as written. Besides the lamp, the sun and the sky light, two low lights shine from opposite corners (one warm, one cool), so the upright faces of a piece differ from one another and its shape shows from either side of the board; the sun was turned down by as much as they add to the board, so the squares look as they did. `resize()` sets the drawing size from `S.pixel` (game pixels per screen pixel; 0 is Max, one per real screen pixel, as in Retro Rack).
- **Settings:** `S` in localStorage (`retroSet.settings`), with `DEFAULTS` at the top of the file: `pixel` 1 and `levels` 256 (the sharpest picture), `dither` and `outline` on, `turn` (on a shared device the view turns round to the player to move), `set` and `finish` (the piece set and finish in use: whatever the locker says is worn, see Cosmetics), `mySet` (online, both sides wear your pieces), `hints`, `autoQueen`, `confirm`, `flat`, `coords`, `lastMove`, `volume` and `vibrate` (see Settings and the menu's tabs). The menu's choices are `M` (`retroSet.menu`: the bot picked, your colour).
- **The board** (the board section): squares of 5.7 cm with a 3 cm border on a round wooden table. Square `s` is centred at (`sqX(s)`, 0, `sqZ(s)`); White sits at +z, so from White's side a1 is at the near left. The squares and the coordinates are one small texture (`drawBoard()`, 16 px a square), the letters and numbers in a 3 × 5 pixel font (`GLYPH`) on all four sides, each set the right way up for the player nearest; with `S.coords` off it is drawn without them. Which board it is comes from the Board slot (`BOARDS`, `applyBoard()`: see Cosmetics). Marks on the squares (`showMarks()`, `MARKS`): the last move (`S.lastMove`), the piece picked up, a king in check (rose), where the piece can go (`S.hints`: a blue dot, or a ring round a piece it can take), and the two squares of a move waiting for Confirm.
- **The pieces** (the pieces section): the shapes and materials come from `sets.js` (see Piece sets and finishes). `makePiece()` builds one piece as a single mesh (the set's shape with the finish's three materials; `lookOf(colour)` says whose set and finish a side wears: yours, or online the other player's for their side), `placeAll(game)` sets out the whole board, with the pieces taken standing beside it on the taker's side (`trayPos()`), and remembers the game shown (`SHOWN`), so `setLook(set, finish)` can change the set or finish and set the table again at once. Every piece faces the other side; knights look to their owner's left, so each player sees the head side on. `pieceIcon()` draws a pixel picture of a piece (the promotion buttons, and the flat view) from the set's own triangles seen from the front, in the finish's colours, every kind at the same scale (or, with `fit`, drawn closer together in size).
- **The flat view** (`S.flat`, the 2D button beside Turn, or Board in the settings): in a game the camera looks straight down and each piece is its picture lying on its square (`FLAT`, `flatMat()`: one flat mesh a piece, the picture drawn about as many pixels tall as a square is on screen, `flatH`), upright for the side the view is on (`cam.base`). The pictures never turn with the view (the owner found that jarring): dragging doesn't turn the flat view, and a turn of the board, after a move or by the Turn button, is a flip at once, not a swing round. Behind the menu and in the waiting room the pieces stay solid (`wantFlat()`, `refit()`). Taps, drags, marks and the moves gliding all work as usual; nothing hops.
- **States:** `menu`, `lobby` (the waiting room of an online game), `play` (waiting for a move), `think` (the computer choosing), `anim` (pieces gliding), `promo` (choosing what a pawn becomes) and `over`. `G` is the game (see Core), `sel` the square picked up and `targets` its legal moves. `vs` is null for two players on one device, or `{ bot, me }` against the computer; online, `NET.on` and `NET.me` (see Online play). `meCol()` is your colour in either. `startGame(game, opp)` starts a local or computer game; `startLocal()` and `startCpu()` (the bot and colour from `M`, Random tossing a coin each game) call it.
- **The computer's turn** (`startThink()`, `thinkTick()`): `C.think()` is stepped for at most 12 ms a frame, and the move waits until the bot has thought for 0.5 to 1.2 s, so it never snaps back instantly (`QUICK` skips the wait for the tests); it holds while the Menu panel is open. Against the computer the view stays on your side (Turn still swings it), you can't pick up its pieces (`mine()`), Take back goes back to before your last move (its reply too), Agree a draw becomes Offer a draw (`offerDraw()`: the bot accepts when a quick search says it's half a pawn or more worse, or, from move 30, level; `toast()` says which), and the result names you and the bot (`resultText()`).
- **Faces** (the faces section): the bots' portraits are Retro Rack's pixel people (`SPRITES`, `drawSprite()`, `portrait()`), on the picker and in the bar beside the bot's name.
- **Moving:** tap a piece then a square, or drag a piece onto a square (`squareAt()` raycasts the pieces, then the board's plane; `tap()`, and the pointer handlers in the input section). Your own move goes through `choose()`: with `S.confirm` on it waits (`pending`, the bar `#confirm` saying "Play Nf3?") until Confirm is tapped, and a tap elsewhere, Cancel or Esc drops it; otherwise, and for the computer's and the other player's moves, `tryMove()` plays it with `C.play()`, then the pieces glide (`animate()`, `glideTick()`: a knight hops, a castling rook jumps, a taken piece flies to the side), then `placeAll()`, `landed()` (the move's sound, and a buzz for a capture or check) and `afterMove()`. A pawn reaching the end opens the promotion choice first (`askPromo()`), unless `S.autoQueen` makes it a queen at once. With reduced motion nothing glides.
- **The camera** (`cam`): behind the menu it circles slowly (with reduced motion it holds still), the picture shifted (`camera.setViewOffset`) into the space the menu panel leaves: to its right, or below it on an upright phone. In a game it looks down from the side of the player to move (`base`, turned by `afterMove()` when `S.turn` is on, or by the Turn button) plus however far the player has turned it (`yawOff`, by dragging across empty space; up and down tilts, `pitch`), far enough back for the board to fit the screen, times `zoom` (the mouse wheel or a pinch). Every value glides to its goal (`cam.goal()`, `cam.update()`).
- **The game's screen:** the bar along the top (White, whose move it is with the last move, Black; your avatar beside You, the computer's face or online the other player's avatar beside theirs), the moves on the right (hidden on phones), and Menu, Take back, Turn and 2D at the bottom left (online, Take back hides and Chat appears) (`hud()`). The panels: Menu (`#pause`, which holds the settings box with a Match tab first: Resume, Agree a draw, Resign, Quit to menu; resigning and the draw need a second tap within 3 seconds, `confirmTap()`), the promotion choice (`#promo`) and the result (`#over`, `showOver()`, `resultText()`: Play again, See the board, Main menu, and against the computer what the game paid, `#overEarn`). Take back works any number of times, also after a mate or a draw on the board, but not after a resignation or an agreed draw. Esc, the back gesture and a tap outside close a panel; in a game the back gesture opens the Menu panel instead of leaving the page (one history entry kept armed, `arm()`).
- **Menus:** `menuGo(name)` shows a screen (`home`, `cos`, `settings`, `cpu`, `online` or `room`). Home, Cosmetics and Settings are the three tabs along the top of the menu (`#hTabs`: Play, Cosmetics, Settings); the other screens have a Back bar (`#mTop`) instead. Back, the back gesture and Esc go to the screen in `BACK` (New room to Online, the rest home). Home has Rejoin (an online game left by accident), Resume (a game saved on this device), Two players, Vs computer and Online, and beside the version what today's gift was (`#gift`); `refreshHome()` keeps it current, and the card for the kind of game saved says a new one replaces it. Vs computer (`renderCpu()`): the ten bots as cards five across (face, name, rating), the picked one's line, You play White / Random / Black, and Play. Online and New room: see Online play. `toMenu(to)` goes back to the menus: home, or from an online game or waiting room, the Online screen (leaving online on purpose: it tells the other player and forgets the game for Rejoin).
- **Settings and the menu's tabs** (the settings panel section): one box of tabs and pages (`#setBox`) serves both the menu's Settings tab and the game's Menu panel; `showSettings(host, inGame)` moves it into whichever is open (`#setHome`, `#setGame`). Its tabs (`settingsTab()`, `SET.tab`): Match (in a game only, and first), Game (Turn the board, Move hints, Always queen, Confirm moves), Board (Flat view, Coordinates, My set only, Last move), Display (Pixel size, Colours, Dithering, Outlines) and Device (Sound, Vibration, Fullscreen). The pages lie on top of one another, so the panel keeps one height whichever shows, and every one fits a phone on its side without scrolling: at most four rows a tab, each note one line. A setting is a row of buttons in `shell.html` (`.seg[data-key]`, each button's `data-v` the value it sets), a default in `DEFAULTS` and, if something must happen at once, a line in `applySetting()`; `renderSettings()` lights the buttons. The left and right arrow keys step through the tabs. Turn the board is left out in a game against the computer or online (`.onlyLocal`).
- **Sound** (the audio section, Retro Rack's synthesiser): every sound is made from a few tones (`blip()`) and bursts of filtered noise (`hiss()`), so there are no sound files. `sfx(kind)`: `move` (a piece set down on wood), `capture`, `castle` (two knocks), `promo`, `check`, `win`, `lose`, `draw`, `ui` (any button) and `prize0` to `prize4` (a case's prize, longer the rarer). Browsers only allow sound after a tap or a key, so the first one starts it (`ensureAudio()`). `S.volume` is 0 to 1; changing it plays a move to hear it by.
- **Phone and screen comforts** (their own section, from Retro Rack): `buzz()` vibrates for a capture and for check where a phone can (`canVibrate`, `S.vibrate`; the row is hidden elsewhere); Fullscreen (`canFull`, `#sFull`) shows where the browser allows it; and on a phone held upright a note says a sideways phone gives a bigger board (`#rotate`, OK hides it for good, `retroSet.rotateHint`).
- **Saving:** a local or computer game is saved after every move (`save()`, localStorage `retroSet.game`: `{ v: 1, start, moves, vs }`, the moves written as e2e4, `vs` the bot, your colour and `paid` once the game has ended and paid out, or null), and `loadSaved()` replays it for Resume, checking every move again (it returns `{ g, vs }`). A finished game is forgotten. An online game isn't saved this way (Rejoin brings it back) and leaves the saved one alone.
- **Installable app:** `game.js` adds the manifest link and registers `sw.js` only on http(s), so a copy opened from disk stays quiet. The version line (`#ver`) shows `BUILD`, which `tools/build.js` stamps with a fingerprint of the game code.
- **For the tests:** `window.__rs` gives the state, the frame count, the triangles drawn each frame, the settings, the position (`fen`), the moves, the result, the piece picked up, the view, the pieces on the board and beside it, `start2(fen)` (a two-player game from any position), `startCpu(bot, me, fen)` (a game against a bot), `vs`, `quick` (set it to skip the bot's pause), `squareScreen(name)` (where a square is on the screen, to tap it), and for the pieces `look(set, finish)`, `sets`, `finishes`, `tris` (the triangles in the pieces on the table), `shape(kind)` (a kind's height and width in the set in use), `mask(kind)` (its outline from the front, filling the height, as pixels), `icon()` and `camSet()` (the view in a game), and for the settings `pending` (a move waiting for Confirm), `flat`, `pitch`, `marks` (how many marks are on the squares), `coords`, `tab`, `soundCount` and `soundsFrom(n)` (the sounds asked for), and for the cosmetics `lock` (the locker), `lockerEdit(fn)`, `LK` (looks.js), `DEVW` and `dev`, `earn`, `day(d)` (the day's gift for a given date), `opening` and `showPrize()`, `worn`, `wear(slot, id)`, `lookOf` and `peerLook`, `fx()` and `bits`, and for trading `trade` (the trade room's state), `tradeSecs` (the countdown's length), `tradeSend(o)` (a raw message) and `startTrade`, so tests can check the page without reaching into its internals. Add to it as the game grows (Retro Rack's `window.__rr` is the model).

### Cosmetics (the locker section of `game.js`; the looks themselves in the scene, board, effects and faces sections and `sets.js`)
- **The saved locker:** `LOCK` (localStorage `retroSet.locker`), a locker as `looks.js` defines it. Every change goes through `lockerEdit(fn)`, which reads the saved copy, changes it and writes it straight back, so two open pages don't undo each other's changes; a `storage` listener shows a change made in another page. `dress()` puts on whatever the locker says is worn (`LOCK.wear`), with a look being tried on (`PRE`) in its place: the set and finish go into `S.set` and `S.finish` (`setLook()`), the rest into `W` (`board`, `room`, `fx`, `avatar`, `marks`).
- **The Cosmetics tab** (`sc-cos`, `renderCos()`, `COS`): **Locker** (`#cLocker`: a tile for each of the seven slots showing what is worn and how much of the slot is owned, and under Unopened the cases and keys in hand; tapping a case opens it), one **slot** (`#cSlot`: only the looks owned, in the catalogue's order, a duplicate with its count; tapping one tries it on behind the menu, `#bEquip` wears it, Back takes it off again) and **Shop** (`#cShop`: the five cases and eight keys; tapping one says its chances or what it guarantees, `#bBuy` buys it). Nothing scrolls and there are no arrows: a slot's looks are a grid of at most sixteen. Trying Square marks on shows a sample of marks on the board (`sampleMarks()`); trying an effect plays it once.
- **Opening a case** (`openCase()`, `OPENING`): a small panel first (`#openBox`) to pick a key in hand (a case needs one), then Open, and the reel and the prize take up the whole screen (`#reelScreen`, the owner's wish: it should feel important). The locker pays and picks first (`LK.open()` with `Math.random`); then a reel of looks from what the key could give, each tile 40% of the screen's height (at most 22% of its width), glides to a stop on the prize over 5.5 s (`REEL`), ticking as each look passes the marker; a tap or Esc skips it, and with reduced motion there's no spin. Then the prize: the other tiles dim, the screen glows in the prize's rarity colour (`--rc`, `.lit`), with slow rays turning behind an epic or better (`.rays`), its name large, New! or a duplicate and its coins, and Equip, Open another and Close.
- **Pictures** (`lookPic()`, `casePic()`, `keyPic()`): every look, case and key as a 32 × 30 pixel picture: a set its knight, a finish a pawn of each side, a board sixteen squares, a room its table and floor, an effect a glyph (`FX_ICON`), an avatar its sprite, marks a sample.
- **What each slot looks like:** Finish in `sets.js` (16, two that move, `SETS.tick()`); Board (`BOARDS`: square, frame and ink colours, `tex` a pattern drawn into every square by `PATTERN`, `glow` a second picture of what shines by itself, `anim`); Room (`ROOMS`, `applyRoom()`: the air, floor and table colours, floor tiles, and `PROPS_OF`, things standing round the edge: bookcases, cafe tables, trees, arcade machines, stars; the lights over the board never change, so the pieces read the same in every room); Square marks (`MARK_LOOKS`, `applyMarks()`: colours, corner brackets or an arrow for the last move, the dots' shape, tints that breathe or flicker); Effects (the effects section, `FX_LOOKS`, `fx(what, square)` for a capture, a check and a checkmate: little flat-coloured bits with a speed, a weight and a life, `fxTick()`; never with reduced motion); Avatar (`AVATARS`, on Retro Rack's sprites with seven more heads). `looksTick()` moves the looks that move. Light squares are kept to mid tones (about as bright as the standard board's), or white pieces wash out on them under the lamp.
- **Earning** (`gamePaid()`, from `afterMove()`): a game against the computer pays once, when it ends (`vs.paid`, saved with the game, so taking the mate back and playing it again pays nothing more); the result panel says what (`EARN`, `earnText()`). Two-player and online games pay nothing. `dailyGift()` runs at start-up and whenever the page comes back into view.
- **Online** (the owner agreed this change to the messages): `hello` carries `look: { set, finish, avatar }`; `peerLook()` accepts only ids the catalogue knows (anything else becomes the free look). Each side's pieces wear their owner's set and finish and each avatar shows beside its player's name, unless `S.mySet` ("My set only") is on. Boards, rooms, marks and effects are your own, on your screen only.
- **Trading** (the trading section of `game.js`, `TR`; the rules are `looks.js`'s, above): the Cosmetics tab's **Trade** page (`#cTrade`, `renderTradePage()`: the open trade rooms in `#trRooms`, `#trCode` and Join with code, Listed / Private `M.trListed`, Create trade room) and the trade room (`#tradeBox`, `renderTrade()`). `startTrade(code, listed)` connects (`trConnect()`) to the relay's room `TRADE` + the code; game codes are at most 8 characters, so the two kinds never meet, and `isTradeRoom()` sorts the one open-rooms list (`renderRooms()` fills both `#roomList` and `#trRooms`; `updateLobbyWatch()` watches on either screen). An invite link is `#trade=CODE`. `leaveTrade()` (Leave, Esc, the back gesture) sends `tbye`. Each side holds `TR.inv` (the other's things), `TR.mine` and `TR.theirs` (the two offers) and `TR.ready` ([me, them]). Messages (`onTrade()`): `thello` (name, `v`, `inv`, `offer`; `re` asks for one back), `toffer`, `task` (`ids` asked for: `TR.asks`, shown one at a time with Add and No), `tno`, `tready` (`on`, and `h`: `trHash()`, both offers written out, which the receiver checks against its own the other way round), `tdone` (`h`) and `tbye`; everything received goes through `LK.cleanOffer()` and is cut to what the sender showed (`trClamp()`). A changed offer (`trChanged()`) or a changed locker (`trFit()`, from the `storage` listener) clears both Ready marks and stops a countdown. Both ready: `trCount()` runs `TR_SECS` (5) seconds, ticking; `trBackOut()` (Back out, Esc) stops both. At the end `trFinish()` sends `tdone` and `trSwap()` swaps through `lockerEdit()` once both `tdone`s describe the same trade; with no answer in 4 seconds (`TR.wait`) it's called off, and the other page told (`tready` off). A different version (`TR.verBad`) can't press Ready. The grid (`trList()`) shows one side's things in one slot or `cases`, theirs perhaps only what you lack (`TR.onlyNew`, `#bTrNew`); `thing(id)` describes a look, `case:grade` or `key:id`.
- **Dev mode** (for the owner, to try every look): typing the dev word as the name on the Online screen switches it on or off (`isDevWord()`, `setDev()`). Only a SHA-256 fingerprint is in the code (`DEVW.print`), and it is Retro Rack's own (of `'retroRack:' + word`), so the same word works in both games; never write the word into the repository. While it's on (`DEV`, localStorage `retroSet.dev`) the locker is a separate test locker with every look, 100,000 coins and 50 of each case and key (`retroSet.lockerDev`, `LK.full()`), the version line says DEV and the coins say (test); switching it off forgets the test locker and brings the real one back.

### The cosmetics' rules (`src/looks.js`, `tools/sim-shop.js`)
- **The catalogue:** `SLOTS` (Pieces `set`, Finish, Board, Room, Effects `fx`, Avatar, Square marks), `RARITIES` and `RARITY` (common to mythic: the colour, and what a duplicate pays), and `ITEMS`, 70 looks, each `{ key: 'slot:id', id, slot, name, rarity, free }`; the first of each slot is free. What a look looks like is drawn elsewhere, by its id.
- **Cases and keys:** `GRADES` (bronze, silver, gold, diamond and `lucky`, the Super Lucky Box: the odds of each rarity, and the shop's price) and `KEYS` (`any`, the standard key, and one for each slot, which guarantees a look for that slot; a key never changes the rarity). `open(locker, grade, key, rnd)` takes one of each and gives `{ item, dupe, coins }`: a rarity with nothing left to win in the key's slot gives way to the nearest that has, rarer first; looks already owned are less likely (`OWNED_WEIGHT`); an epic or better is certain within `PITY` cases; a duplicate pays coins and is counted in the locker; a Super Lucky Box never gives a duplicate, and pays `LUCKY_FULL` coins once nothing is left.
- **Earning:** `gameOver(locker, { id, rating, top }, result)`: a win against the computer pays `winCoins(rating)` and drops a case of `gradeFor(rating)`, the first win against each bot a second case one grade better (a Super Lucky Box for the three strongest); a draw pays a quarter. `daily(locker, day)`: once a local date, `DAILY` coins growing over days running, the seventh bringing a Super Lucky Box. `START` is the starter kit.
- **The locker:** `{ v, coins, owned, cases, keys, wear, beaten, daily, pity, opened }`; `fresh()`, `validate()` (a clean copy of anything saved), `wear()`, `buyCase()`, `buyKey()`, `progress()`, and `full()` (a test locker with everything).
- **Trading:** an offer is `{ items: { 'slot:id': n }, cases: { grade: n }, keys: { key: n }, coins }` (`noOffer()`). `cleanOffer()` makes a safe one of anything (whole numbers, known things, never a free look); `offerEmpty()`; `offerKey()` writes one as a string, the same however it was put together; `canGive()` says whether a locker holds it all; `inventory()` is what a locker shows the other player (its tradeable looks, cases and keys, never its coins); `trade(l, give, get)` makes one side's swap, or returns false with nothing changed, and a worn look given away to its last copy comes off.
- **No `Math.random` here:** every draw takes a generator (`CORE.rng`), so a test or a measurement repeats exactly.
- **The pace is measured, not guessed:** `tools/sim-shop.js` plays out pretend players; `HANDOVER.md`, section 5, has the figures. `tests/looks.test.js` fails if the middle player takes fewer than 11 or more than 17 days.

### Piece sets and finishes (`src/sets.js`)
- **A set is a shape, a finish is a material, and any set can wear any finish.** `SETS.LIST` holds the seven sets: Classic (Staunton shapes), Ornate (the classic shapes dressed up: turned stems, double collars, beads round every foot, a mane and bridle, an arched crown), Minimal (plain turned forms, one mark on top of each), Blocks (stacked from 4.4 mm cubes, like 3D pixel art), Figures (little medieval people: a foot soldier, a castle tower, a rider, a bishop with mitre and crook, a queen, a king with cape and sword), Sci-fi (six-sided machines with lights) and Carved (short and heavy, eight-sided, every corner nudged as if cut by hand). `SETS.FINISHES` holds the sixteen finishes of the Finish slot, their ids and names matching `looks.js`: Classic (ivory with brown trim against a mid purple with pale gold trim), Wood, Chalk, Sea, Forest, Marble, Metal, Ember, Candy, Neon, Ice, Obsidian, Royal, Circuit, and two that move, Rainbow and Molten (`anim`, `tick()`).
- **The modelling kit** (`maker()`): a piece is built in millimetres from boxes, cylinders, balls, octahedra (`gem`), rings, side views given thickness (`slab`) and profiles turned round the upright (`lathe`, with any number of flat sides), each added to one of three slots: 0 the body, 1 the trim (collars, crowns, crosses), 2 the glow (lights). `carve(planes)` cuts away whatever lies inside every plane given (the bishop's cut, `mitre()`: sloping into one side of the head with a smaller head inside as its floor, or a cleft straight down for the Carved set's two horns); `jitter()` nudges corners (Carved); `geo()` turns it into one geometry in metres with a group per slot. Front is -z, and a knight's head points to +x. `STRETCH` makes the Figures stockier, `ROUGH` sets the jitter.
- **`SETS.geo(set, kind)`** makes each shape once and keeps it. **`SETS.mats(finish, colour)`** gives the three materials (flat-shaded, both sides drawn so a cut shows its inside): for each side a finish has `body`, `trim` and `glow` colours and `dark` (a little light of its own, so a dark piece never goes flat black); `lit` and `trimLit` make the glow and trim shine by themselves; `shine`, `gloss` and `spec` make a polished surface (a Phong material instead of Lambert).
- **What each kind must keep** in every set, so it reads at a glance from above: the pawn the smallest and plainest; the rook battlements; the knight a horse (or its head) seen side on; the bishop tall and pointed, with its cut; the queen a ring of points; the king the tallest, with a cross. The `sets` test measures it: with every outline drawn at the same height, no two kinds may differ in less than 12% of their outline, and the pawn and the bishop in less than 30%.
- **Online** each side wears its owner's set and finish (see Cosmetics); `pieceIcon()` and the flat view take a set and finish for the same reason.

### Online play (the online play section of `game.js`, and `relay/`)
Retro Rack's online play, ported as closely as chess allows; its `AGENTS.md` and `HANDOVER.md` explain the design in more depth.
- **The relay** (`relay/src/index.js`) only forwards messages: a `Room` Durable Object per room code (two seats, given by a per-tab client id, so a reload keeps its seat; a third connection is told `full`; rooms nobody uses are deleted after 6 hours) and one `Lobby` for the open-rooms list, pushed to every Online screen watching over a WebSocket (a listed room shows while its host waits; rooms waiting 45 minutes are forgotten). It never plays chess. Migrations `v1` (Room) and `v2` (Lobby); a new Durable Object class needs a **new** tag, never an edit. The listed room's `mode` is the colour its host chose (`random`, `white`, `black`).
- **The address:** `relayBase()` reads `?relay=` from the page's address (the tests and local play) or `window.RETRO_SET_RELAY` from `config.js`, and turns it into a `wss://` (or `ws://`) address. With none, the Online card says "Not set up yet" and the screen explains.
- **Menus:** Online (`sc-online`): your name (`retroSet.name`), the open rooms (`updateLobbyWatch()`, `lobbyConnect()`, `renderRooms()`: watched only while the screen shows; each with Join), Join with code, and Create a room, which opens New room (`sc-room`, `renderRoom()`): You play White / Random / Black (`M.netColour`) and Listed / Private (`M.listed`), then Create room. `startOnline(code, listed, rejoin)` opens the waiting room (`#lobby`: the code, the invite link, Copy invite link, Cancel) and connects (`netConnect()`, reconnecting with a growing pause). An invite link (`#room=CODE` in the address) joins straight away.
- **Messages between players** (`onNet()`): `hello` (name, whether a game is under way, `v` the version, `look` the set, finish and avatar worn), `setup` (the host's start: the position, `white` the seat playing White, `games`), `move` (`n` the move's number, `u` the move as e2e4, `fen` the position after it), `state` (the whole game: the start, every move, `white`, `games`, and a resignation or agreed draw; `fix` when it answers a `resync`), `resync` (please send `state`), `chat` (a preset index only), `resign`, `drawOffer`, `drawYes`, `drawNo`, `again` and `bye`. From the relay: `welcome` (the seat), `peer` (on or off) and `full`.
- **Who plays what:** seat 0 (whoever opened the room) hosts: `hostStart()` picks the colours (the first game as chosen for the room, Random tossing a coin; each Play again swaps them) and sends `setup`; `startOnlineGame()` starts it on both. `NET.me` is this browser's colour; `mine()` lets you pick up only your own pieces on your own move, the bar says You and the other player's name, and the view sits on your side.
- **The check on every move:** your move goes the moment you make it (`tryMove()`). The receiver (`netProcessQueue()`) plays a move only if it's the next one, theirs to make, legal here (`C.playUci()`), and reaches the same position as the sender's (`fen`); otherwise it says so and sends `resync`, and the sender's whole game (`netSendState(true)`, `adoptState()`) replaces it, checked move by move again. Messages that change the game (`state`, `resign`, `drawYes`) wait while a move is gliding (`NET.hold`). While the other player is away (`NET.peer` false, or the relay unreachable), your move isn't played and you're told (`tap()`), since it would go nowhere. Chess sends moves, not physics, so the two games stay in step far more easily than in pool; the checks are for different versions and modified copies.
- **Reconnecting:** each tab has a client id in sessionStorage (`rs.cid`), so a reload keeps its seat and the other player's game sends the whole game (`state` on `hello`). A duplicated tab copies sessionStorage, so each open page marks the id as in use (`rs.live`, cleared on `pagehide`); a copy that finds the mark picks a fresh id (and so joins as the second player in a waiting room, or is told the room is full).
- **Rejoin:** whenever an online game starts, a move is played or a game is restored, the page saves the room code, its client id and the other player's name (`retroSet.rejoin`: a list, one entry per client id, kept 3 hours). The home screen's Rejoin button (`updateRejoin()`) puts the id back into sessionStorage and joins the room; if the other player's page is still open, the game comes back exactly, and if neither is, a fresh game starts in the same room (as in Retro Rack). Each page in a room holds a Web Lock named `retroSet.seat.<cid>` (`holdSeat()`), and the button skips entries whose lock is held, so a second tab never takes over a seat that's still open. Quit, Main menu on the result, Cancel in the waiting room, a full room and the other player's `bye` forget the entry. Two tabs of one browser share the list and each reads, changes and writes it, so they can write over each other's entry when both save at once; a tab in a game that sees the list change without its own entry puts itself back (a `storage` listener).
- **Versions:** `hello` carries `BUILD`. Before a game starts, a mismatch stops it starting and tells both players to reload; mid-game it only warns (`NET.verWarn`), since every move is checked.
- **In a game:** the connection line under the bar (`netBadge()`), quick chat (`CHAT`, `sendChat()`: preset messages only, so there's nothing to moderate in listed rooms; at most one a second or so), Offer a draw (`netOfferDraw()`; the other player sees `#offer`, Accept or Decline), Resign (two taps; the other player is told), Play again (`askRematch()`, `tryRematch()`: both ask, the button saying who's waiting), and Quit. There is no take back online (as in Retro Rack), so its button hides.
- **For the tests:** `window.__rs.net` (on, seat, me, cid, code, peer, link, started, peerName, games) and `__rs.send(o)` (a raw message, as a modified copy could send).

## 4. Key decisions and why

**Delivery (carried over from Retro Rack)**
- **One self-contained `index.html`,** with fonts and three.js inlined, so the game works offline as a single downloaded file and GitHub Pages can serve it with no build step on the server.
- **three.js is pinned at r159** (ES-module build, wrapped by `tools/build.js`), the same file as Retro Rack's, so code ported between the games behaves the same. Upgrading is possible but not needed; if you do, re-check lighting, the `DepthTexture` outline pass and the console.
- **The same pixel-art look:** Retro Rack's low-resolution render target and post-processing shader (outlines, vignette, dithering), its palette and its fonts, so the two games look like a family.
- **The version is a fingerprint of the code,** shown at the bottom of the menu, so the owner can see an update has arrived (and, if online play comes, players can compare versions).
- **The context packs** (`CONTEXT.md`, `CONTEXT-SHORT.md`) are remade by every build and checked by the tests, so any AI can be given the whole project in one file and it's never out of date.
- **Separate from Retro Rack:** its own repository, site, storage keys (`retroSet.` rather than `retroRack.`) and, if online play comes, its own relay, so a change to one game can't break the other. Code is shared by copying, not by a shared library, because each game is one self-contained page.

**The game (chosen by the owner, 7 November 2026)**
- **3D pixel art,** like Retro Rack, rather than a flat 2D board: the setup was already in place and the two games match. A 2D board would have been lighter on phones.
- **All three ways of playing:** two on one device, against the computer, and online. Built in stages, each its own pull request, because all three need the board, the pieces and the rules first: Stage 1 two on one device, Stage 2 the computer, Stage 3 online (which needs its own relay; the owner sets up the Cloudflare Worker, as for Retro Rack).
- **The full rules, no clocks:** castling, en passant, promotion to any piece, check, checkmate, stalemate, and every draw (repetition, fifty moves, too few pieces, agreement). Clocks can come later. "Basic rules first" was advised against: the missing rules are the ones that cause bugs when added later.
- **Classic piece shapes** (Staunton), low-poly and outlined like Retro Rack's balls, rather than toy-like or character pieces: easiest to read at a glance.

**Stage 1: two players on one device (7 November 2026)**
- **The rules engine is plain and checked against the published move counts** (perft) for five standard positions, which catch nearly every move-generation bug (castling through check, en passant pins, promotions). Positions are copied, never changed, so take back is just the previous position, and the computer player can search without undoing moves.
- **Repetition and the fifty-move rule draw at once,** as chess.com does, rather than a player having to claim them (the official rule): there's nobody to claim to on a shared screen, and a claim button would be one more thing on a phone. Too few pieces to mate is the standard list (kings alone, a single bishop or knight, bishops all on one colour of square).
- **Tap a piece then a square, or drag it:** both work on a phone and a computer. Dragging across empty space turns the view; the piece doesn't follow the finger while dragged (it may later).
- **The view turns round to the player to move** (on by default, "Turn the board" in the Menu panel), like turning a real board on a table between two people; off, it stays where it's put, and Turn swings it round by hand.
- **Take back as often as you like,** also after a mate or a draw on the board (friendly games), but not after a resignation or an agreed draw, which aren't moves.
- **Resigning and agreeing a draw need a second tap** within 3 seconds, so a stray tap can't end a game.
- **Knights look to their owner's left:** facing forward, each player only saw the back of a flat head. Side on they read like a printed diagram.
- **Coordinates on all four sides,** each set for the player nearest, in a 3 × 5 pixel font drawn into the board's texture (no font to wait for).
- **A game in progress is saved after every move** and offered as Resume on the home screen, so a closed tab or a phone call doesn't lose it. Starting a new game replaces it, and the Two players card says so.

**Stage 2: the computer opponents (7 November 2026)**
- *These were the first eight bots, Pip (100) to Nell (1500). They were renamed and became ten later ("Bots: ten opponents and real blunders", below): Nell's place at 1500 is now Ted's, and Tariq's at 1300 Daws's.*
- **What the owner asked for:** opponents from 100 to 1500, "very accurate, like chess.com bots". Chosen from the options put to the owner: **eight named bots** at 100, 300, 500, 700, 900, 1100, 1300 and 1500, each with a pixel face and a line about how it plays (15 bots, one every 100 points, was the alternative: twice the faces, and 100 points is hard to feel); **you pick your colour**, Random to start with.
- **How accurate a rating can be (said to the owner before building):** a rating only means something against a pool of players. Chess.com's, lichess's and FIDE's scales differ, by hundreds of points at the low end, and chess.com's own bots are widely felt not to play like people of their stated rating. Nothing here can match chess.com's numbers without playing chess.com's players. Three ways to anchor the numbers were offered: tune each bot's mistakes to published figures for human players at each rating (most like people, most work), anchor to Stockfish's calibrated strength setting and measure the gaps between bots, or measure the gaps only. **The owner chose Stockfish plus measured gaps.**
- **The anchor:** Stockfish 19 (stockfish.js, the full single-threaded engine, installed by the tool into a temporary folder, never part of the game, so its GPL licence doesn't touch the game) has a strength setting, `UCI_Elo`, from 1320 up, calibrated by its makers against an engine rating list (CCRL) rather than people. Nell (1500) is tuned to score 50% against it at 1500, and Tariq (1300) 47% against it at 1320 (20 points above him). Below 1320 there's nothing to anchor to, so each lower bot is tuned to score 24% against the bot above (a 200-point gap). The errors add up down the chain, so the lowest bots are the least certain; the margins are in section 5.
- **Stockfish's time:** 60 ms a move rather than the minute-per-game time its setting was calibrated at. At its weakest settings it chooses after a search only one or two moves deep, which takes a fraction of that, so more time changes little; this was a judgement, not measured.
- **The engine was strengthened before tuning:** at first, looking 3 moves ahead at full effort only just beat Stockfish 1500 (55%, 40 games), which left no room for Nell to make mistakes. Better judgement of positions (passed pawns, pawn weaknesses, rooks on open files, the bishop pair, king shelter) and looking further when in check took that to 64% (80 games); looking 4 moves ahead, 81% (80 games, about 1750). So Nell looks 4 moves ahead and makes slips on purpose, rather than being a machine with nothing to give.
- **Human-like weakness, not random weakness:** the low bots look only one move ahead, so they see a piece left to be taken but miss forks, pins and other threats, as beginners do; every bot sometimes picks a less good move, more often the worse its level (a temperature), plus an occasional outright blunder. The first plan had Pip and Mabel not even following captures through (so they'd grab defended pieces), but measured, that was about 760 points below Dev even at its best, below 100 on this scale, so every bot follows captures through and the knob does the weakening. Styles add a little character (Mabel pushes pawns, Dev grabs captures, Ruth castles early, Tariq likes checks); each bot is tuned with its style on, so the style doesn't change its rating. Bots that look one move ahead still spot a mate in one and avoid stalemate, or they'd never finish a won game.
- **The bot thinks for half a second to a second or so** before moving, even when it has chosen sooner, so the reply doesn't snap back.
- **Take back against the computer** goes back to before your last move, taking its reply too (as on chess.com). **A draw is offered, not agreed:** the bot accepts when a quick search says it's half a pawn or more worse, or, from move 30, level.
- **No resigning by the bots**: they play on to the end, which suits beginners practising mating.

**Bots: ten opponents and real blunders (7 November 2026)**
- **The owner's names, ten of them:** Torben, Alfie, Ollie, Dom, Joseph, Barney, Magnus, Jake, Daws and Ted, weakest to strongest. Of the three options put to the owner (ten bots from 100 to 1500, ten from 100 to 1900, or eight with the first eight names) the owner chose **ten from 100 to 1500**: steps of 150 (the last one 200), so both Stockfish anchors (1500 and 1320) still fit. The lines and faces were written for the game (the owner's choice); the repository is public, so nothing personal is said about anyone.
- **Old saves carry on:** a game or a menu choice from before the renaming moves to the nearest new bot (Pip to Torben, Mabel to Alfie, Dev to Dom, Priya to Joseph, Gus to Barney, Ruth to Jake, Tariq to Daws, Nell to Ted).
- **Real blunders, not random moves:** before, a bot's "blunder" was any legal move at random, which often wasn't a blunder at all. Now each bot has a set chance each move (30% Torben, 24% Alfie, 19% Ollie, 15% Dom, 12% Joseph, 9% Barney, 7% Magnus, 5% Jake, 4% Daws, 3% Ted) of a move that really loses at least two pawns' worth: leaving a piece to be taken, grabbing a pawn that can't be held, walking into a mate or missing one. Of those, it picks the one that looks best at a glance (the position straight after the move, not the reply), as people do: a blunder looks like a good idea. This is chess.com's sense of a blunder: a move much worse than the best one. The chances were set by hand, falling with strength but never zero, as asked; only the middling-move setting (the temperature) was tuned for the ratings.
- **The trade-off (told to the owner):** with blunders this frequent, the low bots' ratings come mostly from their blunders, so tuning turned their temperature down: they play fewer middling moves between the blunders than before (Torben's temperature 93, against 107 for the old 100 bot). Lower blunder chances would bring the middling moves back.
- **Measuring took three rounds:** a tuning run (80 games a step) and then two corrections, each followed by a fresh check of 240 games a bot, ending with every bot within 30 points of its target (section 5). Each correction used the rating points per step of the knob; the second one took them from the bot's two checks, because the tuning steps were too noisy at the low levels, where blunders make strength change slowly with the knob.

**Stage 3: online play (9 November 2026)**
- **As close to Retro Rack as possible (the owner's words):** the same relay (a Room per room code, a Lobby for the open-rooms list, hibernating WebSockets on the free plan), the same screens (Online: your name, the open rooms, Join with code, Create a room; then the room's settings; the waiting room with the code and the invite link to copy), the same invite links, reconnecting by a per-tab id, duplicated tabs, Rejoin for 3 hours, the version check before a game and the warning during one, preset quick chat, Play again needing both players, and leaving on purpose forgetting the game. The code was copied and adapted rather than rewritten, so a fix in one game can be carried to the other.
- **Its own Worker,** `retro-set-relay`, not Retro Rack's, so a change to one game can't break the other. Retro Rack's ideas box (part of its relay) was left out: it isn't online play, and could be ported on its own if wanted.
- **What chess changes:** the room's setting is your colour (White, Random or Black) instead of the type of pool game, and Open rooms shows it; Play again swaps the colours (Retro Rack alternates the break); Retro Rack's re-rack offer becomes a draw offer, accepted or declined; conceding a frame becomes resigning. Only the moves travel, so there's no live aim preview and no "input-only check" of shot physics: instead the receiver plays a move only if it's legal and reaches the same position as the sender's, and otherwise fetches the whole game.
- **No take back online,** as in Retro Rack (which has no undo online). A take-back request, as on chess.com, could be added (section 7).
- **No moving while the other player is away:** the move would go nowhere, so it's held back with a message, as Retro Rack does with a shot.
- **If both players close their apps,** a fresh game starts when they rejoin, as in Retro Rack: the game lives only in the players' open pages. Keeping it would be easy in chess (each page can save the moves) but changes how games start, so it's in the ideas list.
- **Names in Open rooms** are cleaned by the relay (14 characters, no `<` or `>`), as in Retro Rack, and chat is presets only, so there's nothing to moderate.

**The second round (agreed 10 November 2026)**
- **What the owner asked for:** the pieces thoroughly improved, because some kinds looked alike, the bishop and the pawn above all and worst on black; other piece shapes, for cosmetics later (an ornate one, a minimalist one and others); a cosmetics shop with five rarities, as in Retro Rack; streamlined menus with tabs instead of long scrolling screens; more settings (gameplay, visuals, comforts); then a single-player story mode against the bots, like Retro Rack's championships. And to be asked as many questions as each part needs before it's built.
- **The order (the owner's choice):** 1) the pieces and piece sets, 2) tabbed menus and settings, 3) the shop, 4) the story mode; each its own pull request, tried on the live site before the next. The owner had listed the shop before the menus; it was moved after them because the shop is a menu screen and would otherwise be built twice.
- **Why the bishop and pawn looked alike (found by looking):** both were a ball on a collar on a stem, differing only in height, and the usual view looks down at 54 degrees, which squashes height; the black pieces were so dark that no shading showed, leaving only the outline to read; the bishop had no cut in its head, and the king's cross was about 1 cm wide.
- **The fix in the shapes:** every kind has one thing no other has (the pawn a plain ball, the bishop a tall pointed head with the cut, the rook battlements, the queen a ring of points, the king a big cross, the knight a horse's head), and this is measured, not judged by eye alone: with outlines drawn at the same height, the pawn and bishop differ in 44% of their outline in the Classic set, and the closest pair in any set (tall pieces on the same kind of stem, such as bishop and king) in 14% or more.
- **The fix in the light:** two low lights from opposite corners, one warm and one cool, so a piece's upright faces differ from one another; before, every light was overhead and all the side faces were lit alike. The sun was turned down to match, so the board's colours are as they were.
- **Seven sets (the owner chose all four extras offered):** Classic, Ornate, Minimal, Blocks, Figures (medieval), Sci-fi and Carved (squat).
- **Shape and finish are separate (the owner's choice):** any set in any finish, so the shop can have dozens of piece looks across five rarities rather than seven. Classic, Wood, Marble, Metal and Neon exist so far, in plain colours; grain and veining could be painted in when the shop is built.
- **The black pieces' colours (the owner's choice, from pictures of three options):** somewhat lighter, with trim. Black is a mid purple (`#4b446e`, from `#2c2140`) with pale gold trim (`#d9b877`) on the collars, crowns, crosses and the bishop's tip, the parts that tell the kinds apart; white keeps its ivory and gets brown trim (`#b98a4e`) to match. The options not taken: lighter with no trim (cleanest, white unchanged), and staying near-black with the trim (the body was still hard to read).
- **Until the shop exists** every set and finish is free, chosen in the game's Menu panel with < and >. The shop will take that over and lock what hasn't been earned; the owner knows.
- **Nothing is sent online:** each player sees their own set on both sides. Showing the other player's set would change the online messages, so it's a question for the shop.
- **Flagged for later parts:** five piece sets alone can't fill five rarities (Retro Rack has 60 looks), so the shop needs finishes, boards and probably rooms too; a story mode that needs opponents other than the ten bots needs each one measured (about 1½ hours of machine time), never guessed.

**Part 2: the menu's tabs and the settings (10 November 2026)**
- **Tabs on the home screen (the owner's choice, over Retro Rack's cog):** Play, Cosmetics and Settings along the top of the menu. Cosmetics arrives whole in part 3 (the owner's choice, over building the locker half now), so for now there are two tabs, and the piece set and finish chooser stays in the game's Menu.

The < and > chooser in the Match tab is the one place arrows remain, until the locker replaces it.
- **One settings box for the menu and the game,** moved between them, so a setting can never be in one place and missing from the other. In a game a Match tab comes first (Resume, the draw, Resign, Quit).
- **The settings the owner picked (all four offered for play, and for the picture all but one):** Move hints, Always queen, Confirm moves, the flat view; the Display tab (the game had these settings inside it but no screen for them), sound, fullscreen and the phone comforts, coordinates and the last move's tint. Square colour schemes were turned down as a setting: they will be cosmetics, equipped from the main menu.
- **The flat view draws pictures, not the solid pieces from above:** seen from straight above, turned pieces are all circles, which would have been the least readable view in the game. So each piece becomes its own outline from the front, in its set's shape and its finish's colours, lying on the square: a diagram of the set you're using.
- **The flat view's pictures never turn (the owner's correction, 11 November 2026):** at first they turned with the view to stay upright, as it swung round after a move or was dragged, which the owner found very jarring. Now they only ever face the side the view is on: dragging doesn't turn the flat view, and a turn of the board is an instant flip, as on a chess website.
- **Confirm moves marks the two squares and asks "Play Nf3?"** rather than moving the piece and moving it back: nothing on the board changes until the move is real, which matters online, where a move goes the moment it's played.
- **Sound is Retro Rack's synthesiser,** tones and filtered noise made in the page, so there are no sound files to load and a downloaded copy has sound too. A knock for a move, a heavier one for a capture, old-machine notes for check and the result.
- **Not built:** Retro Rack's gliding highlight under the tabs and its sliding pages (the tabs here are a plain underline); a piece following the finger; clocks.

**Part 3 as agreed with the owner: the cosmetics, a locker and a shop (10 November 2026; built 11 November)**
- **A third tab on the menu, Cosmetics,** holding a locker and a shop. "Much more neat and effective, no arrows and long scrolling" (the owner's words): like Fortnite's locker.
- **The locker:** an overview showing what is equipped in every slot at once, and the cases and keys owned but not yet opened. Opening a slot shows the catalogue of what you own of that type; tapping an item previews it on the board, and an Equip button makes it stick (the owner's choice, over tapping to equip at once).
- **Seven slots:** Pieces (the set), Finish, Board (the square colours: turned down as a setting, wanted as a cosmetic), Room (table, floor, walls, lamp), Effects (captures, check, checkmate), Avatar (a pixel face beside your name) and Square marks (the last-move tint, the dots, the check warning).
- **About 70 items at launch** (the owner's choice, over about 40 or about 110), roughly 7 piece sets, 16 finishes, 12 boards, 6 rooms, 8 effects, 12 avatars and 9 square marks, in five rarities as in Retro Rack. The owner signs them off from picture sheets after they are built, swapping out or renaming what they don't like.
- **Everyone starts with Classic only:** the Classic set and finish and the standard board, room, marks and a plain avatar. The other six sets and four finishes, free in the game's Menu today, become things to earn. A secret word (only its fingerprint in the code, as in Retro Rack) gives the owner a test locker with everything.
- **Cases are earned and bought; keys are bought.** Four grades of case (Bronze, Silver, Gold, Diamond): the case sets the odds of each rarity. Every case needs a key. A standard key opens a case for any type of cosmetic; a type key (one for each slot) guarantees that type. Keys guarantee a type, never a rarity (the owner's design).
- **The Super Lucky Box (the owner's idea and name):** a case above Diamond with better odds that never gives a duplicate. Given for milestones (the first win against each of the three strongest bots, a seven-day login streak) and sold in the shop at a high price.
- **Duplicates** from the other cases pay some cash and stay in the inventory as a count, so there is something to trade later.
- **Earning (the owner's choices):** beating the bots (coins by the bot's rating, a case for the first win against each, a fraction for a draw), a daily login gift that grows over a streak, and a starter kit (some coins, a case and a key). Online wins pay nothing: the result would be trusted from the player's own browser.
- **Pace: about two weeks** for a regular player (three or four wins a day) to fill the locker (the owner's choice, over two months or six months). The story mode's rewards, in part 4, will therefore need things of their own to give.
- **Online, each side's pieces wear their owner's set and finish, and each player's avatar shows beside their name,** with a setting, "Show my set on both sides", for anyone who finds the other player's set hard to read. This changes the online messages (`hello` will carry the looks; only known ids accepted), so both players need the new version, which the game already checks.
- **Trading comes after part 3, as its own pull request (the owner's wish):** an honour system for now, in trade rooms separate from the rooms for playing. Told to the owner: lockers live in each player's own browser, so anyone can edit their save and give themselves anything; real scarcity needs accounts and lockers held on a server, a separate project.
- **Agreed for trading besides (the owner said yes to each):** changing either offer takes both Ready marks off, so nothing can be swapped out at the last moment; when the countdown ends the two pages confirm to each other before anything moves, and the trade is called off if either is silent (lockers live in each browser, so a connection dropped at that instant can still leave a trade half done: rare, not impossible); the dev mode test locker can trade, so the owner can hand a look to a friend; the open list needs the relay to accept a `trade` room; the seven free looks can't be traded; and each player sees only the coins the other puts into the offer, not how many they have. (The relay change turned out not to be needed: see "Trading as built".)
- **Trading as the owner described it (11 November 2026):** a swap that both sides agree, of any number of items at once. Everything can be traded: duplicates, your only copy of a look, unopened cases and keys, and coins. Each player sees the other's inventory, with a filter that can be switched on and off showing only what you don't have yourself. You mark an item you want and ask for it to be added to what they will trade to you; that sends them a short notification, and it is theirs to add. When you are happy you press a button called Ready. When both have pressed Ready a countdown of 5 seconds starts; either player can back out during it, and nothing happens until the timer is up. Trade rooms are joined by a code or invite link, and can also be listed for anyone to join, like open game rooms.

**Trading as built (11 November 2026)**
- **A Trade page in the Cosmetics tab,** beside Locker and Shop: the open trade rooms, Join with code, Listed or Private, and Create trade room. A trade room is a large panel over the menu: Your items and Their items, the two offers side by side ("You give", "Bo gives"), a row of the seven slots plus Cases & keys, a grid of at most sixteen things, and along the foot what is going on, Ask for it, Back out and Ready. Nothing scrolls, on a phone on its side or an upright one.
- **No change to the relay.** The plan was to teach the relay a `trade` kind of room for the open list. Instead a trade room's name on the relay is `TRADE` and its code (`TRADEW8J5X`), and the game tells the two lists apart by that: game codes are at most 8 characters, so a game room can never be a trade room, and typing a trade room's code on the Online screen opens an empty game room, not the trade. So the relay needs no new version and nothing on Cloudflare changes.
- **The new messages** go only between two pages in a trade room, never in a game: `thello` (name, version, what you have to trade, your offer), `toffer`, `task` (asking for things), `tno`, `tready` (with the whole trade written out, so a Ready for a different trade isn't counted), `tdone` and `tbye`. What arrives is cut down to what the catalogue knows and the sender showed they have (`LK.cleanOffer()`); a different version is told to reload and can't press Ready.
- **When a trade happens:** both Ready, then 5 seconds on each screen. At the end each page sends `tdone` with the trade written out, and swaps in its own locker once it has sent its own and received the other's, both describing the same trade. If either is missing (a dropped connection, a back-out at the last instant), nothing moves on that page; a page that hears nothing for 4 seconds calls the trade off and tells the other. The one gap, as told to the owner: if a connection drops in the fraction of a second between the two `tdone`s, one page can swap and the other not.
- **A changed offer stops everything:** both Ready marks go, and a countdown stops. So does the locker changing under you (another tab opening a case): the offer is cut to what you still hold and you're told.
- **Asking:** you mark things in their list (a dashed outline), then Ask for it; they see "Ada asks for Wood." with Add and No, and you hear which. Up to eight asks wait in line.
- **Long offers** show as pictures only (the name on hover), so they all fit in the strip.
- **No Rejoin for trade rooms:** a reload comes back through the address (`#trade=CODE`), and nothing is lost by leaving, since nothing has moved.

**Part 3 as built (11 November 2026)**
- **The looks were signed off from picture sheets** ("it seems good on the whole"), with one correction, to the flat view (part 2, above).
- **A slot shows only what is owned,** as the owner asked ("your catalogue of owned cosmetics"), with how much of the slot that is (5 of 16). What else exists is found by opening cases; the shop says each case's chances.
- **One pattern everywhere:** tap to choose, then a button to act (Equip in a slot, Buy in the shop, Open on a case), so nothing is worn, bought or opened by a stray tap. The owner chose this for the locker; the shop and cases follow it.
- **The reel takes up the whole screen (the owner's change, 11 November 2026: "making it important").** The first version spun in a small panel for three seconds. Now the whole screen dims, each look on the reel is 40% of the screen's height, it spins for five and a half seconds with a tick as each look passes, and the prize is shown large with the screen glowing in its rarity's colour, and rays turning slowly behind an epic or better. A tap skips the spin. Retro Rack's fuller show (stripes, sparkles, confetti, a shake for a mythic) could still be ported.
- **A game pays once.** Take back works against the computer, also after a mate, so without this a won game could be taken back and won again for ever. It also means an easy win can be had by taking back mistakes: the bots are for practice, and the cosmetics are only cosmetics.
- **The dev word is Retro Rack's own,** checked against the same fingerprint, so the owner has one word for both games and nothing new to remember. It is typed as the name on the Online screen, as there.
- **The pieces chosen in the old Menu chooser are forgotten:** everyone starts in Classic and earns the rest, as agreed. The chooser itself is gone: looks are put on from the main menu only.
- **Online only the pieces and the avatar are shown to the other player.** Boards, rooms, marks and effects are each player's own, on their own screen: a board or room is how you like to see the game, and the other player may find yours hard to read.
- **Not built, for later:** Retro Rack's collections and their rewards; a money counter on every screen; saving the locker to a file; the gift announced anywhere but the home screen.

**A fault found while testing part 3 (11 November 2026)**

A tab in a game that sees the list change without its own entry now puts itself back. Four runs out of four pass since. It matters because the owner tests online play in two tabs.

## 6. How things are tested

- **Rules:** `tests/core.test.js` (28 tests): perft counts for five standard positions, castling, en passant, promotion, pins, checkmate, stalemate, each draw, resigning, take back, notation and saving, and that the context packs are up to date.
- **The cosmetics' rules:** `tests/looks.test.js` (29 tests, trading's rules among them), and the pace by `tools/sim-shop.js` (section 5).
- **Engine and bots:** `tests/bots.test.js` (18 tests): the cast, blunder chances, the renaming, the knob, the evaluation, mates, captures, what happens without following captures, real blunders, seeds, legal moves, a whole bot game. Their strength: `tools/sim-bots.js` (section 5).
- **The browser:** headless Chromium (Playwright) with software WebGL (SwiftShader). The page exposes `window.__rs` (state, position, moves, where each square is on the screen and so on) to make scripting easy; the `play` and `cpu` tests play with real mouse taps and drags at those positions. `node tests/browser/run-all.js` runs them all (see `AGENTS.md`, Testing): `file`, `fit`, `play`, `cpu`, `online`, `rejoin`, `sets`, `settings`, `locker` and `app` (485 checks in all).
- **The live relay can't be reached from Claude Code's cloud sessions:** their network refuses `workers.dev` addresses. So the browser tests always use a local relay, and the live one is checked by the owner in a browser (its address should say "Retro Set relay is running.", and two tabs should play each other).
- **Online:** the real Cloudflare runtime runs locally (`npx wrangler dev`, on port 8797), and the game is opened with `?relay=ws://127.0.0.1:8797` in **separate browser contexts**, so each gets its own client id. After every move both windows' positions and moves must match. Covered: the invite link, colours, a reload, chat, draw offers, Play again, a doctored move, an absent opponent, resigning, duplicated tabs, different versions before and during a game (a copy of the site with its version changed), Rejoin in every case Retro Rack covers.
- **Software WebGL is slow,** so keep test windows small (about 480×360) unless the size is what's being tested.

## 8. How changes are made

- Work happens in Claude Code, which pushes to GitHub through its GitHub connector.
- **Node.js** is needed for `node tools/build.js` and `node tests/core.test.js`. If it's missing, install the LTS version from nodejs.org.
- **The routine** (details in `AGENTS.md`, "How changes are made"): describe a change; Claude Code explains the options and builds the one chosen on a branch, rebuilds `index.html`, runs the tests and opens a pull request. When the owner says "merge it", it is squash-merged into `main`, and the live site updates a minute or two later (Ctrl+F5 to see it).
- **Keep it to one change at a time.** Test online changes with the local relay before merging, since both players need the same version.
- **After a squash-merge,** Claude Code brings its working branch level with `main` by merging `main` into it (the files end up the same) rather than overwriting the branch: force pushes are refused in its cloud sessions.
- **The relay deploys itself:** Cloudflare Workers Builds rebuilds `retro-set-relay` on each push to `main`. If a relay build fails, its log is under the Worker's Deployments tab in Cloudflare (Copy build log).
- **To undo a change,** revert it and push the revert, so the site goes back to how it was.

**Suggested first message in a new session:**
> Read AGENTS.md and HANDOVER.md. Run the tests and the build, and tell me whether everything is working. Don't change or push anything yet.

**To give another AI the whole project:** give it the link https://raw.githubusercontent.com/flopp-r/retro-set/main/CONTEXT.md (or the file itself). If it can't take a file that size, use `CONTEXT-SHORT.md`.

# Retro Set

3D pixel-art chess, a sister to Retro Rack. Play a friend on one device or online, or ten computer opponents from 100 to 1500, with the full rules.

Play it at https://flopp-r.github.io/retro-set/

## What's in this folder

| File | What it is |
|---|---|
| `index.html` | The game. It works on its own, even opened straight from your computer. |
| `config.js` | One setting: your relay address, so online play knows where to connect. |
| `relay/` | A tiny Cloudflare Worker that passes messages between the two players of an online game. |
| `sw.js`, `manifest.webmanifest`, `icons/` | Let people install the game as an app and play it offline. |
| `src/`, `vendor/`, `tools/`, `tests/` | The source code, the 3D engine and fonts, the build tool and the tests. `index.html` is built from these. |
| `AGENTS.md`, `CLAUDE.md`, `HANDOVER.md` | Notes for AI assistants and developers: how the project fits together and how to change it (`CLAUDE.md` points Claude Code to `AGENTS.md`), and its history and decisions. |
| `CONTEXT.md`, `CONTEXT-SHORT.md` | The whole project in one file, for an AI that can't open this repository (see "Asking another AI about the project" below). Made by the build; don't edit them. |

Everything here runs on free plans. You need a GitHub account and, for online play, a Cloudflare account; everything is done in your web browser.

## Step 1: Put the game on GitHub Pages

Do this once, after the setup has been merged into the `main` branch (it's done already for Retro Set).

1. Sign in to github.com and open https://github.com/flopp-r/retro-set.
2. Go to the repository's **Settings**, then **Pages** in the left sidebar. Under **Build and deployment**, set **Source** to **Deploy from a branch**, choose the **main** branch and the **/ (root)** folder, then click **Save**.
3. Wait a minute or two and refresh the page. It will show the site address, `https://flopp-r.github.io/retro-set/`. Open it: you should see the Retro Set title in front of a board, and the version at the bottom of the panel.

GitHub occasionally renames buttons. If something doesn't match exactly, look for the closest option with the same meaning.

## Step 2: Put the relay on Cloudflare

(Done for Retro Set: the relay is live at `https://retro-set-relay.floppr.workers.dev`. These steps are for setting up a copy of your own.)

Online play needs a relay: a tiny program on Cloudflare that passes the moves between the two players. Retro Set has its own, separate from Retro Rack's, so a change to one game can't break the other. You do this once, the same way as for Retro Rack.

1. In the Cloudflare dashboard, open **Workers & Pages** (it may be under **Compute** in the sidebar) and click **Create application** (once just **Create**).
2. Choose **Import a repository** and click **Get started**. If asked, give Cloudflare access to the `retro-set` repository (in GitHub's settings for the Cloudflare app, add `retro-set` to the repositories it can see).
3. Pick the `retro-set` repository.
4. Set the project name to exactly `retro-set-relay`. It must match the name in `relay/wrangler.jsonc`.
5. Open the advanced or build settings and set the **Root directory** (sometimes called **Path**) to `relay`. Leave the build command empty (Cloudflare may fill in `npm run build`: delete it, or the build fails, because the relay has nothing to build), and leave the deploy command as `npx wrangler deploy`.
6. Click **Save and Deploy** and wait for the build to finish, which takes a minute or two.
7. Open the new Worker. Its address looks like `https://retro-set-relay.yourname.workers.dev`. Visit that address in your browser; it should say **Retro Set relay is running.**

Cloudflare occasionally renames buttons. If something doesn't match exactly, look for the closest option with the same meaning.

## Step 3: Connect the game to the relay

(Done for Retro Set: `config.js` holds the address.)

1. On GitHub, open `config.js` in the repository and click the **pencil** icon to edit it.
2. Paste your relay address between the quotes on the last line, so it looks like this:

   ```js
   window.RETRO_SET_RELAY = "https://retro-set-relay.yourname.workers.dev";
   ```

3. Click **Commit changes**. GitHub Pages updates within a minute or two. (Or give Claude Code the address: it's public, not a secret, and it can make the change.)

From then on, every change to `relay/` merged into `main` is deployed to Cloudflare by itself.

## How to play

- **Moving:** tap a piece, then the square to move it to (blue dots show where it can go; a ring means it can take a piece there). Or drag the piece onto the square. To castle, move the king two squares towards the rook.
- **Promotion:** when a pawn reaches the far side, choose what it becomes.
- **The view:** drag across an empty part of the screen to turn the board round, or up and down to tilt it. Zoom with the mouse wheel, or pinch on a phone. After each move the view turns round to the player whose move it is; switch that off under **Menu**, **Turn the board**. The **Turn** button swings the board round by hand.
- **Take back** undoes the last move (as often as you like).
- **Menu:** its first tab, Match, has resign, agree a draw (both need a second tap, so a slip can't end the game) and quit; the tabs beside it are the settings. On a phone, the back gesture opens it.
- **Settings** (the Settings tab on the main menu, or the tabs in a game's Menu): **Game** has Turn the board, Move hints (the dots), Always queen (no promotion question) and Confirm moves (each move waits for a tap on Confirm); **Board** has Flat view (straight down at flat pictures of the pieces, like a diagram; the **2D** button in a game does the same), Coordinates and Last move; **Display** has Pixel size, Colours, Dithering and Outlines; **Device** has Sound, and where the device allows them Vibration and Fullscreen.
- **Cosmetics** (the Cosmetics tab on the main menu): the **Locker** shows what you're wearing in seven slots (Pieces, Finish, Board, Room, Effects, Avatar, Square marks) and the cases and keys you hold. Tap a slot to see the looks you own, tap one to try it on the board behind the menu, and **Equip** to wear it. Tap a case to open it with a key: a standard key gives a look for any slot, a slot's own key always gives one for that slot. The **Shop** sells cases and keys for coins. Coins and cases come from beating the computer (more for stronger opponents, and a better case the first time you beat each one) and from a gift on each day you open the game. Online, the other player sees your pieces and avatar; **My set only** in Settings, Board, shows your own pieces on both sides instead.
- **Trading** (Cosmetics, **Trade**): make a trade room, listed for anyone or private, and send the link, or join one from the list. You see the other player's looks, cases and keys (switch on **Only what I don't have** to hide what you already own) but not their coins. Tap your own things, and type coins, to put them in the trade; tap theirs and **Ask for it** to ask for them. When you're both happy, both press **Ready**: after 5 seconds the swap happens in both lockers, and **Back out** stops it until then. Changing either offer takes both Ready marks off. The looks everyone starts with can't be traded. It works on trust: each locker is kept in its owner's own browser.
- **The end of a game:** checkmate, stalemate, the same position three times, fifty moves each without a capture or a pawn move, or too few pieces left to checkmate.
- **Resume:** a game in progress is saved after every move. If you close the page, the home screen offers **Resume** next time.

## Playing the computer

Choose **Vs computer**, pick an opponent and your colour (White, Black or Random), then **Play**.

| Opponent | Rating | How they play |
|---|---|---|
| Torben | 100 | Has just learnt how the pieces move, and leaves them anywhere. |
| Alfie | 250 | Loves pushing pawns, and forgets the pieces behind them. |
| Ollie | 400 | Grabs anything you offer, even when it's a trap. |
| Dom | 550 | Gets the queen out early and goes hunting. |
| Joseph | 700 | Knows a few openings, then loses the thread. |
| Barney | 850 | A club-night regular. Takes any piece you leave loose. |
| Magnus | 1000 | Plays it safe: castles early and waits for you to slip. |
| Jake | 1150 | Steady. Rarely hangs a piece, but sometimes drifts. |
| Daws | 1300 | Sharp tactics: looks for checks and captures first. |
| Ted | 1500 | The strongest here. Gives very little away. |

- **How they play:** like people, every one of them makes real blunders (leaving a piece to be taken, grabbing a pawn that can't be held, missing a mate), Torben on nearly a third of his moves and Ted on about one in thirty, as well as plenty of middling moves.
- **What the ratings mean:** they're measured, not guessed. Ted and Daws were tuned by playing hundreds of games against Stockfish at its official strength settings (1500 and 1320), and each of the others to be 150 points below the one above, which means the stronger one wins about seven games in ten. Measured over 240 games each, every bot came out within 30 points of its rating (the lower the bot, the wider the margin: about ±45 for Ted up to ±145 for Torben). They are close to, but not the same as, chess.com ratings: every site's scale is a little different, especially at the low end.
- **Take back** undoes your last move and the computer's reply. **Menu** has **Offer a draw** (the computer accepts only if it thinks it's worse, or the game is level late on) and **Resign**.

## Playing online

1. Open the game, choose **Online**, and type your name.
2. To join a friend, pick their room from **Open rooms** and click **Join**, or type their code into **Join with code**.
3. To host, click **Create a room**, choose your colour (**White**, **Random** or **Black**) and **Listed** or **Private**, then click **Create room**. You get a five-character room code and an invite link: click **Copy invite link** and send it. Opening the link joins your room straight away.
4. Listed rooms show under **Open rooms** for anyone; private ones are only for people with the code or the link.

- **In the game:** the line under the names says whether your opponent is connected. **Chat** sends a quick message from a short list. **Menu** has **Offer a draw** (your opponent accepts or declines), **Resign** and **Quit**. There's no take back online.
- **Play again:** when a game ends, both press **Play again** and a new game starts with the colours swapped.
- **Lost connection or reloaded the page?** You go straight back to your seat, and the game carries on.
- **Closed the app by accident?** For 3 hours the home screen shows **Rejoin your game with …**. If your opponent's game is still open, you're back exactly where you were; if both of you closed it, a fresh game starts in the same room.
- **Play yourself:** open a room in one tab, then open the invite link (or duplicate the tab) for the other side.
- **Versions:** both players need the same version. If not, the game says so: reload (Ctrl+F5 on a computer, or close and reopen the app on a phone).

## Installing it as an app

- **On a computer (Edge or Chrome):** open the game's address, then click the install icon at the right-hand end of the address bar (or the browser's menu, then **Apps**, then **Install this site as an app**).
- **On Android (Chrome):** open the address, tap the menu (⋮), then **Add to home screen** or **Install app**.
- **On iPhone or iPad (Safari):** open the address, tap **Share**, then **Add to Home Screen**.

The app updates itself: when you're online it always loads the latest version, and the saved copy is only used when there's no internet.

## If something isn't working

- **GitHub Pages shows a 404:** give it a few more minutes, and make sure Pages is set to the `main` branch and the `/ (root)` folder, with `index.html` at the top level of the repository.
- **The Online card says "Not set up yet":** the relay address isn't in `config.js` yet (steps 2 and 3).
- **Stuck on "Connecting…":** check the address in `config.js`. It should start with `https://` and end with `workers.dev`, with nothing else inside the quotes. Visit the address directly to confirm it says the relay is running.
- **Cloudflare build fails mentioning the name:** make sure the Worker is called `retro-set-relay`, or change `"name"` in `relay/wrangler.jsonc` to match.
- **"That room already has two players in it":** someone else is in that room. Create a new one.
- **"…different versions of Retro Set":** both players reload (Ctrl+F5 on a computer, or close and reopen the app on a phone), then come back to the room.
- **You still see the old version after an update:** press Ctrl+F5 on a computer, or close and reopen the app on a phone. The version is shown at the bottom of the menu, so you can compare it with the one Claude Code tells you.
